# Task 17.1: OCaml Tree Layout Program

## Goal
Write an OCaml script that loads a saved state file using `load_state` from `stochastic_estimator.ml`, computes radial layout positions, and outputs a flat array of nodes with `(x, y, color, parent_index)` for Deck.gl rendering.

## Context
This is the combined steps 1 & 2 of Task 17 (Search tree visualization). Since we're doing the layout in OCaml, there's no intermediate file between extraction and layout — just one program that loads the tree, processes it, and outputs the final format.

The full task has two parts:
1. **OCaml program** (this task) — load tree, compute layout, output flat array
2. **Deck.gl rendering** (Task 17 step 3) — WebGL, handles GPU + zoom/pan + aggregation

## What needs to be done

### Script: `treeviz/tree_layout.ml`
- Takes two arguments: `<puzzle-file> <state-file>`
  - `puzzle-file`: Used to construct the search space (provides type `'a`)
  - `state-file`: The saved state to load and walk (e.g., `saves/pinned/estimate-state.backup`)
- Uses `Stochastic_estimator.load_state` to reconstruct the tree in memory
- Walks the reconstructed tree (recursive traversal of `children` arrays)
- Computes radial layout positions using:
  - **Proportional arc subdivision**: each subtree gets angle proportional to its *max width*
  - **Node-local adaptive radial spacing**: `R_{d+1} = R_d × (1 + 2π/N_d)`
- Outputs flat array of nodes to `tree-data.json` for Deck.gl

### Node types → Colors
Derived from node properties:
- `"Result"` — leaf with solution (`num_choices = 0`, `solution_estimate > 0.5`, `has_solution = true`)
- `"Fail"` — leaf that failed (`num_choices = 0`, `solution_estimate ≈ 0`, `has_solution = false`)
- `"Fork"` — branching node not yet fully explored (`num_choices > 0`, `is_completed = false`)
- `"Completed"` — fully explored branching node (`num_choices > 0`, `is_completed = true`)

### Visual properties (for coloring in visualization)
- Color mapping: Result=green `[100,255,100,200]`, Fail=red `[255,100,100,200]`, Fork=blue `[100,150,255,200]`, Completed=gray `[180,180,180,200]`
- `has_solution`: bool — does this subtree contain at least one solution? (`solution_estimate > 0`)

### Output format
Flat array of nodes with parent pointers — Deck.gl consumes this directly:
```json
{
  "nodes": [
    { "x": 0, "y": 0, "color": [100, 150, 255, 200], "parent_index": -1 },
    { "x": 10, "y": -5, "color": [100, 255, 100, 200], "parent_index": 0 },
    { "x": -8, "y": 3, "color": [255, 100, 100, 200], "parent_index": 0 },
    ...
  ]
}
```

- `x`, `y`: computed radial layout position (float)
- `color`: RGBA tuple `[r, g, b, a]` (0-255) — derived from node type
- `parent_index`: index of parent node (-1 for root)
  - Edges are implicit: renderer draws line from each node to `nodes[parent_index]`
  - No separate edges array needed
- **Flat structure** (not nested) — efficient for 500K+ nodes, Deck.gl loads as flat arrays
- **Output to file** (`tree-data.json`) — Deck.gl loads via URL

## Design decisions needed (for approval)

1. **Arguments**: Two args (puzzle file + state file) vs one arg (just state file)?
   - Two args needed because `load_state` requires a search space of the correct type
   - Alternative: hardcode for oracle2/hexominoes only

2. **Output location**: File (`tree-data.json`) vs stdout?
   - Deck.gl loads data via URL, so file is required
   - OCaml writes `tree-data.json` directly — no piping needed

3. **Color format**: RGBA tuples vs hex strings?
   - Deck.gl expects `[r, g, b, a]` arrays (0-255) for `getFillColor`
   - RGBA is more flexible than hex (supports transparency)

4. **Error handling**: What if state file doesn't match puzzle type?
   - `load_state` will fail at runtime — should we catch and report nicely?

## What NOT to do (yet)

## Success criteria
- Script runs on `saves/pinned/estimate-state.backup` with the oracle2 puzzle file
- Outputs valid flat JSON array (`tree-data.json`) with ~500K nodes (or whatever the saved state contains)
- Node types are correctly classified and mapped to RGBA colors
- Parent-child relationships preserved via `parent_index` pointers (-1 for root)
- Deck.gl can load the output file and render nodes + edges with zoom/pan
